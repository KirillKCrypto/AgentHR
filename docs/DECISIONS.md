# DECISIONS — AgentHR

Зафиксированные решения и компромиссы. Перед спорным выбором проверить этот файл;
новое решение — добавлять сюда, а не в `AGENTS.md`.

## Архитектура и стек

| Решение | Обоснование |
|---|---|
| Модульный монолит, не микросервисы | скорость разработки, минимум инфраструктуры |
| Deep Agents как основной Harness | готовый цикл, контекст, планирование, сабагенты, память; свои правила — middleware |
| LangGraph под капотом Deep Agents | явное состояние, checkpointing, контроль tool-calling |
| Дефолтный состав Deep Agents | файловые tools и сабагент `task` оставлены; своей мультиагентной логики в MVP нет |
| Postgres + pgvector, одна БД | меньше инфраструктуры; векторный поиск без второй системы |
| Граф в Postgres на MVP | реляционная модель; репозиторий-граница для будущей миграции на Neo4j/AGE |
| React + TS, не Python-UI | стриминг интервью, кастомные визуализации, кодогенерация |
| Без state-менеджеров | TanStack Query + `useState` закрывают потребности |
| JWT access + refresh | просто и стандартно |
| Упрощённый планировщик в MVP | полный топологический маршрут — позже |

## Данные и онтология

| Решение | Обоснование |
|---|---|
| Пайплайн M2: сервис + tools | извлечение и нормализация — детерминированный `app/services/analysis.py`; те же функции — tools агента |
| Онтология — словарь, не whitelist | навыки вне словаря не теряются и попадают в кандидаты/автотемы |
| TTL/CSV — источники, не готовая OWL-модель | в TTL нет иерархии, уровней и пререквизитов; они добавляются отдельными слоями |
| Provisional-темы | у каждого навыка всегда есть `topic_id`; неизвестный навык получает provisional-тему, алиас и кандидата |
| Backfill legacy NULL | миграция заполнила старые `topic_id`, затем `NOT NULL` и FK `RESTRICT` |
| Лимит `AUTO_TOPIC_LIMIT` | не даёт онтологии взрываться; overflow идёт в одну review-тему |
| Ревью через CLI | в проекте нет ролей/админ-аутентификации; CLI безопаснее публичного API |
| Автоматическое ревью provisional-тем | сначала правила (точный alias или близость ≥ `ONTOLOGY_AUTO_MERGE_SIMILARITY` → merge; упоминания в нескольких документах → approve), затем LLM только для спорных тем; `approve`/`merge` применяются при `confidence` ≥ `ONTOLOGY_AUTO_REVIEW_MIN_CONFIDENCE`, merge — только в top-5 кандидатов; решение `keep` и низкая уверенность уводят навык в общую canonical-тему «Прочее (авто-ревью)», поэтому ручная проверка пользователю не нужна; provisional остаётся только при недоступной LLM; аудит с `actor="auto"`; запуск best-effort после сохранения документа |
| Две метрики покрытия | `coverage_all` включает provisional, `confirmed_readiness` — только canonical |
| Группы `AND/OR` | `OR` — max, `AND` — min; для confirmed группа должна быть полностью canonical; закрытые требования считаются по группам: `OR` закрыта при любом закрытом варианте, `AND` — только целиком; альтернатива с личным пробелом помечается `covered_by_alternative` |
| Criticality и рубрика уровней | `must_have` / `nice_to_have`; `required_level` 0–100 по якорям; `critical_readiness` — доля полностью закрытых обязательных групп, частичный разрыв не даёт 100%; критический гейт — позже |
| Тесты по темам плана | 10 вопросов из банка `questions`, по 2 на сложность; варианты ответа генерируются LLM лениво, перемешиваются и кэшируются; проверка и метрика детерминированные; одна попытка на тему, результат сохраняется в `topic_test_results` и обновляет профиль (`source="test"`); assessment-подсистема удалена |
| Интервью | только по конкретной вакансии, до 8 вопросов; свободный ответ и оценка по рубрике; сессия стартует с одного вопроса, сложность следующей темы меняется на шаг по ответу, при слабом ответе добавляется follow-up (1 на тему, 2 на сессию); фидбек стримится через SSE, оценка сохраняется до потока; итог обновляет профиль с `source="interview"`; интервью можно проходить повторно |
| Сложность по уровню вакансии | уровень сохраняется в `vacancies.level`; заголовок вакансии приоритетнее ответа модели, поэтому «Senior» в названии не теряется при ошибочном `middle`; junior/middle — только сложности 1 и 3, senior/lead — 1, 3 и 5 с упором на 3–5; старые вакансии без уровня оцениваются по заголовку, затем по медиане `required_level`; если вопроса нужной сложности нет, он генерируется лениво, fallback на другую сложность — только при сбое генерации |
| Итоги интервью | детерминированный отчёт `GET /interviews/{id}/report`: темы с оценкой ≥ 70 — сильные, ниже — «что подтянуть» с упущенными пунктами; незатронутые темы считаются только для интервью по вакансии; до завершения отчёт отвечает 409 |
| Интервью по вакансии | `POST /interviews` принимает только `vacancy_id`: интервью привязано к конкретной вакансии, plan-сессии остаются только историей и не показываются в списке. |
| Оценка ответа | LLM не выставляет общий score. Она возвращает разбор: `correctness` 0–50, `coverage` 0–30, `depth` 0–20, `relevance`, `point_assessments` и `critical_errors`; сервис считает score сам и применяет caps: off-topic ≤ 20, критическая ошибка ≤ 45. Для пограничных 40–84 делается второй вызов и берётся среднее. Разбор сохраняется в `interview_turns.score_breakdown`. |
| Локальные эмбеддинги | ONNX-модель без ключей и внешних сервисов; деградация к alias/fuzzy; таблица `embeddings` позже |
| Профиль-first | сначала резюме и профиль знаний, затем вакансия; резюме в форме вакансии не требуется; повторное резюме дополняет профиль, а не заменяет его |
| Резюме файлом | PDF/DOCX через `POST /resumes/upload`: `pypdf`/`python-docx`, лимит 5 МБ и защита от zip-бомб; файл не хранится, только текст; сканы без текстового слоя → 422 |
| План подготовки | темы из слабых мест: разрывы требований вакансии, слабые и незатронутые темы последнего интервью, низкий уровень и уверенность профиля; 5–12 тем, цель — требование вакансии или 100; повторный запрос переиспользует план только для той же вакансии и при неизменном профиле/интервью |
| Постоянный план | `learning_plans.profile_fingerprint` — SHA-256 по `user_skill_states`, `vacancy_id`, требованиям вакансии, последнему завершённому интервью и версии алгоритма; при совпадении `POST /plans` возвращает существующий план с HTTP 200 и `reused=true`, иначе создаёт новый и архивирует прежний план этой вакансии |
| Банк вопросов | полная генерация по 90 seed-темам × 5 сложностей × 5 вопросов; CLI по умолчанию добирает сложности 1–5; LLM-ответы кэшируются в БД, дедуп по fingerprint; недостающие вопросы генерируются лениво при интервью с двумя попытками |
| ООП и алгоритмы в тестах | темы `oop` и `algorithms` всегда генерация вопросов, даже если их нет в резюме; в план они попадают только по общим правилам |
| Таймаут и повтор LLM | `OPENAI_TIMEOUT_SECONDS` по умолчанию 60; `extract_vacancy_requirements` при таймауте или обрыве соединения делает один повтор на уровне сервиса, остальные ошибки и второй таймаут уходят как 502 |
