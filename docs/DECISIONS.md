# DECISIONS — AgentHR

Зафиксированные решения и компромиссы. Перед спорным выбором проверить этот файл;
новое решение — добавлять сюда, а не в `AGENTS.md`.

## Архитектура и стек

| Решение | Обоснование |
|---|---|
| Модульный монолит, не микросервисы | скорость разработки, минимум инфраструктуры |
| Deep Agents как основной Harness | готовый цикл, контекст, планирование, сабагенты, память; свои правила — middleware |
| LangGraph под капотом Deep Agents | явное состояние, checkpointing, контроль tool-calling |
| Дефолтный состав Deep Agents | файловые tools и сабагент `task` оставлены; своей мультиагентной логики в MVP нет |
| Postgres + pgvector, одна БД | меньше инфраструктуры; векторный поиск без второй системы |
| Граф в Postgres на MVP | реляционная модель; репозиторий-граница для будущей миграции на Neo4j/AGE |
| React + TS, не Python-UI | стриминг интервью, кастомные визуализации, кодогенерация |
| Без state-менеджеров | TanStack Query + `useState` закрывают потребности |
| JWT access + refresh | просто и стандартно |
| Упрощённый планировщик в MVP | полный топологический маршрут — позже |

## Данные и онтология

| Решение | Обоснование |
|---|---|
| Пайплайн M2: сервис + tools | извлечение и нормализация — детерминированный `app/services/analysis.py`; те же функции — tools агента |
| Онтология — словарь, не whitelist | навыки вне словаря не теряются и попадают в кандидаты/автотемы |
| TTL/CSV — источники, не готовая OWL-модель | в TTL нет иерархии, уровней и пререквизитов; они добавляются отдельными слоями |
| Provisional-темы | у каждого навыка всегда есть `topic_id`; неизвестный навык получает provisional-тему, алиас и кандидата |
| Backfill legacy NULL | миграция заполнила старые `topic_id`, затем `NOT NULL` и FK `RESTRICT` |
| Лимит `AUTO_TOPIC_LIMIT` | не даёт онтологии взрываться; overflow идёт в одну review-тему |
| Ревью через CLI | в проекте нет ролей/админ-аутентификации; CLI безопаснее публичного API |
| Автоматическое ревью provisional-тем | сначала правила (точный alias или близость ≥ `ONTOLOGY_AUTO_MERGE_SIMILARITY` → merge; упоминания в нескольких документах → approve), затем LLM только для спорных тем; `approve`/`merge` применяются при `confidence` ≥ `ONTOLOGY_AUTO_REVIEW_MIN_CONFIDENCE`, merge — только в top-5 кандидатов; решение `keep` и низкая уверенность уводят навык в общую canonical-тему «Прочее (авто-ревью)», поэтому ручная проверка пользователю не нужна; provisional остаётся только при недоступной LLM; аудит с `actor="auto"`; запуск best-effort после сохранения документа |
| Две метрики покрытия | `coverage_all` включает provisional, `confirmed_readiness` — только canonical |
| Группы `AND/OR` | `OR` — max, `AND` — min; для confirmed группа должна быть полностью canonical; закрытые требования считаются по группам: `OR` закрыта при любом закрытом варианте, `AND` — только целиком; альтернатива с личным пробелом помечается `covered_by_alternative` |
| Criticality и рубрика уровней | `must_have` / `nice_to_have`; `required_level` 0–100 по якорям; `critical_readiness` — доля полностью закрытых обязательных групп; `readiness = coverage × critical_gate`, `critical_gate = 0.7 + 0.3 × critical_readiness`; диапазон `readiness_low…high` по средней уверенности |
| Свидетельства уровня | `user_skill_states.evidence_type` (`self_report`, `test`, `interview`) и `verified_level`; тест и интервью подтверждают уровень, резюме остаётся самоотчётом |
| Повторение тем | после теста/интервью тема получает `review_due_at` и `review_interval_days`: слабые — 1 день, средние — 3/7, сильные — до 14; дашборд показывает «Пора повторить», план получает бонус к приоритету |
| Тесты по темам плана | 10 вопросов из банка `questions`, по 2 на сложность; варианты ответа генерируются LLM лениво, перемешиваются и кэшируются; проверка и метрика детерминированные; две попытки на тему, в прогресс и профиль идёт лучший результат; попытки хранятся в `topic_test_results` (`attempt_no`), профиль обновляется без понижения (`source="test"`); assessment-подсистема удалена |
| Качество вариантов ответа | правильный ответ не должен быть длиннее дистракторов: проверка `correct_len <= max(distractor_len)` и `<= 1.2 × средняя`; промпт требует одинаковую длину и запрещает маркеры-подсказки; при провале — вторая генерация, затем 422; старые варианты перепроверяются при старте теста |
| Обязательные темы плана | в план по вакансии попадают все `must_have`, даже с нулевым разрывом; лимит 12 применяется только к `nice_to_have`; `plan_items.criticality` хранит признак; на странице вакансии любой навык можно подтвердить тестом без плана |
| Навигация | верхнее меню: Дашборд, Вакансии, Планы, Профиль; `/plans` разделяет планы по вакансиям и общий; профиль разбит на `/profile`, `/profile/resumes`, `/profile/skills`, `/profile/tests` |
| Интервью | только по конкретной вакансии, до 8 вопросов; свободный ответ и оценка по рубрике; сессия стартует с одного вопроса, сложность следующей темы меняется на шаг по ответу, при слабом ответе добавляется follow-up (1 на тему, 2 на сессию); фидбек стримится через SSE, оценка сохраняется до потока; итог обновляет профиль с `source="interview"`; интервью можно проходить повторно |
| Сложность по уровню вакансии | уровень сохраняется в `vacancies.level`; заголовок вакансии приоритетнее ответа модели, поэтому «Senior» в названии не теряется при ошибочном `middle`; junior/middle — только сложности 1 и 3, senior/lead — 1, 3 и 5 с упором на 3–5; старые вакансии без уровня оцениваются по заголовку, затем по медиане `required_level`; если вопроса нужной сложности нет, он генерируется лениво, fallback на другую сложность — только при сбое генерации |
| Итоги интервью | детерминированный отчёт `GET /interviews/{id}/report`: темы с оценкой ≥ 70 — сильные, ниже — «что подтянуть» с упущенными пунктами; незатронутые темы считаются только для интервью по вакансии; до завершения отчёт отвечает 409 |
| Интервью по вакансии | `POST /interviews` принимает только `vacancy_id`: интервью привязано к конкретной вакансии; если по вакансии уже есть `in_progress`, возвращается она (HTTP 200) с сохранёнными ответами, новая создаётся только после завершения; plan-сессии остаются только историей и не показываются в списке. |
| Таймер ответа | на каждый вопрос 300 секунд от момента показа; дедлайн хранится на сервере, таймер переживает перезагрузку и повторный вход; после дедлайна обычный ответ отклоняется, таймаут фиксируется как `expired`; запас 60 секунд на сеть и распознавание |
| Голосовой ввод | запись целиком через MediaRecorder, аудио уходит в отдельный STT-сервис GigaAM, затем в редактируемое поле ответа; аудио не сохраняется, по умолчанию режим ввода текстовый; сервис запускается отдельным Docker profile `voice` |
| Оценка ответа | LLM не выставляет общий score. Она возвращает разбор: `correctness` 0–50 (только факты, не полнота), `coverage` 0–30 (essential/supporting), `depth` 0–20, `relevance`, `point_assessments` и `critical_errors`; сервис считает score сам и применяет caps: off-topic ≤ 20, критическая ошибка ≤ 45. Второй вызов делается только при `confidence < 0.45`. Разбор и тайминги сохраняются в `interview_turns.score_breakdown`. |
| Латентность оценки | SSE-событие `evaluation` сразу отдаёт score и сессию; frontend показывает оценку, не дожидаясь потокового фидбека. Потоковый анализ привязан к id отвеченного вопроса. Ответ модели компактный (без текстов пунктов и дублирующих массивов); пустой ответ повторяется один раз, чтобы не отдавать 502. В `score_breakdown` пишутся `evaluation_ms` и `feedback_ms`. Замеры: оценка 2–23 с в зависимости от ответа LLM, фидбек 1.5–3.9 с; второй проход при confidence ≥ 0.45 не выполняется. |
| Локальные эмбеддинги | ONNX-модель без ключей и внешних сервисов; деградация к alias/fuzzy; таблица `embeddings` позже |
| Профиль-first | сначала резюме и профиль знаний, затем вакансия; резюме в форме вакансии не требуется; повторное резюме дополняет профиль, а не заменяет его |
| Резюме файлом | PDF/DOCX через `POST /resumes/upload`: `pypdf`/`python-docx`, лимит 5 МБ и защита от zip-бомб; файл не хранится, только текст; сканы без текстового слоя → 422 |
| План подготовки | темы из слабых мест: разрывы требований вакансии, слабые и незатронутые темы последнего интервью, низкий уровень и уверенность профиля; 5–12 тем, цель — требование вакансии или 80; повторный запрос переиспользует план только для той же вакансии и при неизменном профиле/интервью |
| Постоянный план | `learning_plans.profile_fingerprint` — SHA-256 по `user_skill_states`, `vacancy_id`, требованиям вакансии, последнему завершённому интервью и версии алгоритма; при совпадении `POST /plans` возвращает план с `reused=true`, иначе создаёт новый и архивирует прежний план этой вакансии |
| Дашборд | `/dashboard` собирает готовность выбранной вакансии, фокусные пробелы, последнее интервью с дельтой, незавершённое интервью, историю, прогресс плана, тесты и активность; вакансия по умолчанию — последняя загруженная |
| Служебная тема авто-ревью | `other-auto-review` — не учебная тема: исключена из плана, тестов, интервью и прямых запросов вопросов; в профиле остаётся только как служебная |
| Сохранение прохождения | сессия и ответы хранятся в БД; повторный запуск интервью продолжает активную сессию, дашборд показывает «Продолжить интервью», неотправленный черновик ответа хранится в `localStorage` |
| Прогресс плана | `GET /plans/{id}/progress`: только лучший результат теста по теме, равный вес `1/N`; внутри теста балл уже взвешен сложностью вопросов. Резюме и интервью не двигают прогресс. Показываются `tests_completed`, `tests_passed`, `average_score`, `attempts_count`, `next_topic_key/name` и статус темы |
| Метрики готовности | `skill_metric`: `self_level` из резюме/ручной оценки, `verified_level` из теста/интервью, `effective = max`; `vacancy_metric`: `potential_readiness` по `effective`, `verified_readiness` только по подтверждённому, `critical_verified`, `evidence_coverage`, `band`, `blockers`, `confirmation_queue`. Бэнд `ready` требует verified ≥ 80%, critical_verified = 100% и evidence_coverage ≥ 80%. `needs_confirmation` — potential ≥ 60% при verified < 60% |
| Отчёт сессии | `/reports/:id` показывает score/level, дельту к прошлому интервью, средние `correctness/coverage/depth`, сильные/слабые/незатронутые темы и разбор каждого вопроса |
| Банк вопросов | полная генерация по 90 seed-темам × 5 сложностей × 5 вопросов; CLI по умолчанию добирает сложности 1–5; LLM-ответы кэшируются в БД, дедуп по fingerprint; недостающие вопросы генерируются лениво при интервью и при старте теста по теме |
| ООП и алгоритмы в тестах | темы `oop` и `algorithms` всегда генерация вопросов, даже если их нет в резюме; в план они попадают только по общим правилам |
| Таймаут и повтор LLM | `OPENAI_TIMEOUT_SECONDS` по умолчанию 60; `extract_vacancy_requirements` при таймауте или обрыве соединения делает один повтор на уровне сервиса, остальные ошибки и второй таймаут уходят как 502 |
