# Онтология AgentHR

Документ фиксирует, что именно лежит в основе нормализации навыков, gap-анализа и
оценки готовности, какие данные были использованы и что ещё нужно для действительно
объективной оценки кандидата.

---

## 1. Что содержат исходные датасеты

### `hr_ontology.ttl`

Это **не OWL-онтология правил** в классическом смысле. Файл содержит:

| Сущность | Количество | Что это |
|---|---:|---|
| `hr:Skill` | 76 | плоский словарь канонических навыков |
| `hr:Vacancy` | 28 | примеры вакансий |
| `hr:Requirement` | 35 | требования вакансий |
| `hr:Candidate` | 344 | кандидаты |
| `hr:Evidence` | 1635 | свидетельства «кандидат указал навык» |

Что есть в TTL:

- `skos:prefLabel` — каноническое название навыка;
- `skos:altLabel` — 49 альтернативных написаний;
- `hr:category` — грубая категория;
- `hr:requirementLogic` — `SINGLE` (33), `OR` (1), `AND` (1);
- `hr:verificationStatus` — у всех 1635 свидетельств `unverified`;
- `hr:sourceField` — например, `resume_declared_skill`.

Чего в TTL **нет**:

- иерархии `subClassOf` / `broader` / `narrower`;
- пререквизитов и связей между навыками;
- уровней владения (`proficiency`) и рубрик;
- весов и критичности требований;
- различия «обязательно» / «желательно»;
- evidence strength, recency и подтверждённости.

Вывод: TTL — это полезный **словарь навыков и примеров свидетельств**, но не готовая
модель для оценки. Его главная недооценённая часть — `requirementLogic`: требование
может быть одиночным, альтернативой (`R or Java`) или конъюнкцией
(`Docker and Kubernetes`). Если разворачивать требования в плоский список, альтернатива
превращается в два обязательных gap'а, а конъюнкция теряет связь между навыками.

### `skills_curated.csv`

76 строк, 14 исходных категорий, все со статусом `curated_alias_dictionary`.
Суммарно 1705 упоминаний в резюме кандидатов и 37 упоминаний в вакансиях.
Лидеры по упоминаниям в резюме: Machine Learning (176), Python (156), Data Analysis
(83), Excel (79), SQL (73), Project Management (70).

Эти частоты **нельзя** использовать как вес требований вакансии: это смещённая
выборка резюме, а не рынок труда. Их разумно использовать только для приоритизации
алиасов и ревью словаря.

### Что даёт такая модель

1. **Точное сопоставление вместо broad-тем.** `PostgreSQL`, `Kafka`, `Docker`,
   `Kubernetes`, `FastAPI`, `Tableau` и `Excel` теперь отдельные темы, а не «вне
   онтологии» или алиасы `sql`.
2. **Русские и английские алиасы.** `SQL-запросы`, `Docker-образы`, `A/B-тесты`,
   `CI/CD`, `Power BI`, `Node.js` нормализуются к нужной теме.
3. **Граф пререквизитов.** Например: `PostgreSQL → SQL`, `Kubernetes → Docker`,
   `Docker → Linux`, `FastAPI → Python + HTTP API`, `ML → Python + статистика`.
   Это основа для плана подготовки в M3: при провале темы план спускается к её
   пререквизиту.
4. **Контроль качества словаря.** Тесты проверяют:
   - все 76 канонических навыков из `skills_curated.csv` находят тему;
   - алиасы уникальны после нормализации;
   - ключи уникальны;
   - пререквизиты ссылаются на существующие темы;
   - граф ацикличен.

### 2.1. Provisional-темы: навыков вне онтологии больше нет

Статического словаря недостаточно: новые технологии появляются быстрее, чем
обновляется seed. Поэтому в БД добавлен слой **provisional-тем**:

- `topics.status`: `canonical` / `provisional` / `merged` / `rejected`;
- `topics.origin`: `seed` / `auto` / `manual` / `import`;
- `topics.canonical_topic_id`: цель слияния для merged-темы;
- `topic_aliases`: уникальный `normalized_alias` на всю онтологию;
- `topic_candidates.topic_id`: provisional-тема, созданная для кандидата.

Инвариант этапа 1:

> При сохранении резюме или вакансии каждый извлечённый навык получает `topic_id`.
> Если совпадения нет, `resolve_or_create_topics()` в той же транзакции создаёт
> provisional-тему, алиас и запись в очереди ревью.

Provisional-тема участвует в матчинге следующих документов, поэтому одно и то же
написание переиспользуется, а не создаётся заново. Она ещё не считается
подтверждённой: после сохранения документа запускается автоматическое ревью
(см. 2.3), а нерешённые темы остаются на ручную проверку.

### 2.2. Backfill и защита от взрыва онтологии

Миграция `c9a1d2e3f4b5`:

- находит исторические `resume_skills`/`vacancy_skills` с `topic_id = NULL`;
- привязывает их к canonical/provisional-темам по exact/alias;
- для остатка создаёт provisional-темы, алиасы и кандидатов;
- делает `topic_id` обязательным (`NOT NULL`);
- меняет FK с `SET NULL` на `RESTRICT`, чтобы тему нельзя было удалить,
  пока на неё ссылаются навыки.

Лимит `AUTO_TOPIC_LIMIT` (по умолчанию 10) ограничивает число **отдельных**
provisional-тем на документ. Если лимит исчерпан, остальные новые навыки
привязываются к одной теме «Новые навыки (на ревью)»: `raw_name` сохраняется,
`topic_id` остаётся заполненным, а онтология не растёт бесконтрольно.

### 2.3. Автоматическое ревью, merge и аудит

После `commit` сохранения вакансии или резюме выполняется best-effort автопроверка
созданных provisional-тем (`app/services/ontology_auto_review.py`). Ошибка ревью
не ломает загрузку документа: изменения откатываются, документ остаётся сохранённым.

Политика гибридная:

1. **Правила.** Точное совпадение с canonical-темой/алиасом или косинусная
   близость не ниже `ONTOLOGY_AUTO_MERGE_SIMILARITY` (по умолчанию `0.9`) →
   `merge`. Тема, упомянутая в `ONTOLOGY_AUTO_APPROVE_MIN_DOCUMENTS` документах
   (по умолчанию 2) и не имеющая близкой canonical-темы → `approve`.
2. **LLM только для спорных тем.** DeepSeek получает название, свидетельства и
   top-5 ближайших canonical-тем и выбирает `approve` / `merge` / `keep`.
   Решение применяется, только если `confidence` не ниже
   `ONTOLOGY_AUTO_REVIEW_MIN_CONFIDENCE` (по умолчанию `0.75`); `merge`
   разрешён только в тему из показанного списка.
3. **Безопасный fallback.** Всё остальное остаётся `provisional`:
   `auto_review_decision = keep`, `auto_review_confidence`,
   `auto_reviewed_at`. Служебная тема «Новые навыки (на ревью)» всегда
   остаётся на ручной разбор. Повторная проверка выполняется, когда кандидат
   накопил новые упоминания (`auto_reviewed_occurrences`).

Каждое решение пишется в `ontology_review_actions` с `actor = "auto"` и деталями
(источник решения, уверенность, причина, число документов). После `approve`
навыки получают `match_method = auto_approve`, после `merge` — `auto_merge`.
Предохранитель `ONTOLOGY_AUTO_REVIEW_MAX_TOPICS` (по умолчанию 20) ограничивает
число тем и LLM-вызовов за один прогон.

Ручной CLI остаётся fallback и средством пакетной проверки:

```bash
uv run python -m app.ontology.review list
uv run python -m app.ontology.review auto            # повторный прогон всех provisional-тем
uv run python -m app.ontology.review auto --limit 50
uv run python -m app.ontology.review approve <key> --actor reviewer
uv run python -m app.ontology.review reject <key> --actor reviewer
uv run python -m app.ontology.review merge <source_key> --into <target_key> --actor reviewer
```

Правила ручных действий:

- `approve` переводит provisional в canonical;
- `reject` разрешён только для темы без ссылок из резюме/вакансий, иначе
  требуется merge;
- `merge` переносит навыки документов, `user_skill_states`, алиасы, кандидатов
  и рёбра `REQUIRES`; source помечается `merged` и получает `canonical_topic_id`;
- каждое действие пишется в `ontology_review_actions` (актор, source/target,
  детали, время).

HTTP API ревью пока не добавлен: в проекте нет ролей/админ-аутентификации,
поэтому CLI безопаснее. API появится после введения ролей.

### 2.4. Покрытие и подтверждённая готовность

Gap-анализ теперь отдаёт две метрики:

- `coverage_all` — взвешенное покрытие всех требований, включая provisional;
- `confirmed_readiness` — покрытие только canonical-требований; `null`, если
  подтверждённых требований нет.

Дополнительно возвращаются `provisional_count`, `provisional_weight` и
`confirmed_weight`. В профиле у темы есть `status`, в разрыве — `topic_status`,
поэтому UI показывает непроверенные темы отдельным блоком и помечает их
«на проверке». `overall_readiness` сохранён как синоним `coverage_all` для
совместимости.

### Важное следствие для оценки

Раньше `PostgreSQL` матчился в `sql`, а `Kafka` считалась «вне онтологии» и не входила
в готовность. Теперь это отдельные требования. Поэтому у кандидата, который знает
SQL, но не подтверждал PostgreSQL, gap по PostgreSQL становится больше, а readiness
снижается. Это **ожидаемое поведение**: знание SQL не равно знанию конкретной СУБД.
Если нужна частичная преемственность, её следует добавлять явно как правило
инференса, а не как скрытый alias.

## 3. Чего ещё не хватает для объективной оценки

Онтология — только словарь и граф. Объективность оценки определяется ещё четырьмя
слоями, которых пока нет в MVP.

### 3.1. Группы требований `AND` / `OR`

Реализовано:

- `vacancy_skills.requirement_group` — идентификатор группы;
- `vacancy_skills.requirement_logic` — `SINGLE` / `AND` / `OR`;
- LLM-схема извлечения вакансии возвращает `group` и `logic`;
- миграция `e2f3a4b5c6d7`.

Правила оценки:

- `SINGLE` — обычное требование, вес = вес навыка;
- `OR` — засчитывается лучший вариант, вес группы = максимальный вес альтернативы;
- `AND` — все элементы обязательны, оценка группы — минимум, вес = сумма весов.

Для `confirmed_readiness` группа учитывается только если все её элементы
опираются на canonical-темы. Это консервативно, но не даёт provisional-альтернативе
поднять подтверждённую готовность.

### 3.2. Критичность и обязательность

Реализовано:

- `vacancy_skills.criticality`: `must_have` / `nice_to_have`;
- миграция `f3a4b5c6d7e8`;
- LLM-схема извлечения вакансии возвращает `criticality`;
- `required_level` задаётся по рубрике:
  - 0 — не требуется;
  - 20 — знать термин;
  - 40 — базово применять;
  - 60 — рабочий уровень;
  - 75 — уверенный самостоятельный;
  - 90 — экспертный;
  - 100 — эталонный.

Gap-анализ отдаёт `critical_count`, `critical_weight`, `critical_gap_count`.
Критический гейт (снижение итоговой готовности при незакрытом `must_have`)
пока не применяется — это этап 6.

### 3.3. Уровни и свидетельства

Резюме — самоотчёт. В TTL все 1635 свидетельств помечены `unverified`, и это
правильная модель. Для объективности нужно разделять:

- `claimed_level` — что заявил кандидат;
- `verified_level` — что подтверждено интервью/оценкой;
- `evidence_type` — работа, проект, образование, самоотчёт;
- `years`, `recency`, `depth`;
- `confidence` — уверенность извлечения, а не уверенность в навыке.

Рубрика уровня (пример):

| Уровень | Значение |
|---:|---|
| 0 | нет свидетельств |
| 20 | знает термин |
| 40 | базовое применение |
| 60 | рабочий опыт |
| 75 | уверенный самостоятельный опыт |
| 90 | экспертиза / наставничество |
| 100 | автор технологии / признанный эксперт |

Уровень из резюме должен вычисляться по рубрике и типу свидетельства, а не быть
свободным числом от LLM. Итоговая оценка должна показывать диапазон
`readiness_low … readiness_high`, а не ложную точность вроде `93.7%`.

### 3.4. Формула готовности

Целевая формула:

```
effective_level = shrink(claimed_level, evidence_strength)
coverage = min(1, effective_level / required_level)
group_score = OR ? max(items) : AND ? min(items) : coverage
readiness = Σ(weight × group_score) / Σ(weight)
readiness = critical_gate × readiness
```

где `critical_gate` снижает итог, если не закрыто обязательное требование.
Дополнительно:

- пререквизиты дают **частичный кредит** только по явному правилу и с дисконтом;
- `confidence` влияет на ширину диапазона, а не маскируется под точный балл;
- «покрытие» и «готовность» — разные метрики: первая показывает взвешенное среднее,
  вторая учитывает критический гейт.
