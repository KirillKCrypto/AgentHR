## 1. Что это за проект

Персональный AI-агент, который изучает уровень пользователя, формирует его профиль знаний,
выявляет пробелы и адаптирует подготовку под каждую новую вакансию.

**Это не чат-бот.** Главная ценность проекта:

```
LLM + Agent Harness + Tool Calling + Knowledge Graph + Persistent Memory + Adaptive Learning
```

**Основной пользовательский сценарий:**

1. Пользователь загружает описание вакансии.
2. Загружает своё резюме.
3. Получает анализ текущего уровня знаний.
4. Получает персональный план подготовки.
5. Проходит тренировочные технические собеседования.
6. Получает анализ ошибок и рекомендации.
7. Продолжает подготовку на основе накопленного опыта.

## 2. Архитектура

### 2.1 Схема компонентов

```
Frontend (React SPA)
    │ REST + WebSocket
Backend API (FastAPI)          ← auth, бизнес-логика, владелец БД, запуск сессий
    │
    ├── Agent Harness (LangGraph) ──► LLM Agent
    │        │ Tool Calls                 │
    │        ▼                            │
    │   Tools (реестр) ◄──────────────────┘   ← только tools трогают данные
    │
    ├── Knowledge Graph (Postgres: topics + prerequisites + user_skill_states)
    ├── Vector Store (pgvector)
    └── Database (PostgreSQL: сессии, ответы, оценки, audit-лог)
```

### 2.2 Ответственность компонентов

| Компонент | Ответственность |
|---|---|
| **Frontend** | Загрузка резюме/вакансий, отображение профиля/плана/прогресса, проведение интервью, отчёты |
| **Backend API** | Аутентификация, REST-эндпоинты, сервисный слой, транзакции, запуск агентских сессий, трансляция стрима |
| **Agent Harness** | Центральный оркестратор: цикл агента, состояние, маршрутизация tool-calls, лимиты, audit-лог |
| **LLM Agent** | Принятие решений: анализ, планирование, выбор инструментов, генерация вопросов/оценок |
| **Tools** | Типизированные функции (JSON Schema) — единственный способ агента дотянуться до данных |
| **Knowledge Graph** | Онтология тем + зависимости + пользовательский срез уровня |
| **Database** | Источник истины (пользователи, вакансии, резюме, сессии, ответы, audit-лог) |
| **Vector Store** | Эмбеддинги резюме/вакансий/тем/ошибок (семантический поиск) |

### 2.3 Три железных правила

1. **LLM не обращается к БД/графу напрямую** — только через Tools.
2. **Все действия агента логируются** (audit-лог: шаг, tool, аргументы, результат, токены, время).
3. **Состояние сессии сохраняется** (checkpoint) — сессию можно продолжить/восстановить.

### 2.4 Потоки данных

**A. Onboarding.** Вакансия + резюме → `extract_vacancy_requirements` / `extract_resume_skills` →
нормализация к онтологии → профиль знаний (`update_user_skill_state`).

**B. Планирование.** «Требуется вакансией − текущий уровень» → gap-анализ → приоритизированный план.

**C. Интервью (реалтайм).** Генерация вопроса → ответ → `evaluate_answer` → обновление графа →
`adjust_difficulty` → следующий вопрос → `save_interview_result` + отчёт.

**D. Память.** При новой вакансии агент стартует с `load_user_profile` — накопленный профиль переиспользуется.

## 3. AI-агент

### 3.1 Задачи агента

Анализ вакансии/резюме · оценка уровня · планирование маршрута · генерация вопросов ·
оценивание ответов · адаптация сложности и темы · рефлексия и обновление памяти.

### 3.2 Инструменты (tools)

**Чтение / понимание**

- `extract_vacancy_requirements(text) → {skills, level, topics}`
- `extract_resume_skills(text) → {experience, projects, skills, self_level}`
- `get_vacancy_requirements(vacancy_id)`
- `get_user_skill_state(user_id)`

**Граф знаний**

- `query_skill_dependencies(skill_ids)`
- `compute_learning_path(user_id, vacancy_id)` — упрощённая версия в MVP
- `update_skill_proficiency(user_id, skill_id, score, evidence)`
- `find_related_topics(topic)`

**Память (vector)**

- `semantic_search(query, collection, top_k)`
- `get_similar_mistakes(user_id, topic)`

**Интервью**

- `next_question(session_id, strategy)`
- `evaluate_answer(session_id, answer) → {score, topics, gaps, feedback, confidence}`
- `adjust_difficulty(session_id)`

**Память / логирование**

- `save_interview_result(session_id, report)`
- `load_user_profile(user_id)`
- `log_agent_action(...)` — внутренний, вызывается Harness'ом

### 3.3 Что проходит через Agent Harness

Всё, что идёт от LLM к внешнему миру:

- валидация схемы вызова и прав на инструмент;
- исполнение инструмента;
- возврат результата в контекст LLM;
- audit-лог;
- лимиты: max-итерации, бюджет токенов, таймауты;
- checkpoint состояния;
- потоковая передача сообщений пользователю.

### 3.4 Состояние

- **Сессионное (короткое):** цель, история диалога, активный план, стратегия, счётчик шагов, текущая тема/сложность.
- **Рабочее (среднее):** контекст интервью, оценки за сессию, кандидаты на обновление графа.
- **Долговременная память:** профиль знаний + история сессий + семантический слой.

### 3.5 Долговременная память — три уровня

1. **Профиль знаний** — срез графа: тема → уровень, история изменений, evidence.
2. **История собеседований** — сессии, вопросы, ответы, оценки, отчёты.
3. **Семантическая память** — эмбеддинги (резюме, вакансии, темы, ошибки).

Механика: всегда старт с `load_user_profile`, после сессии — обновление графа и сводка.
Память переиспользуется между вакансиями — это ключевое отличие от чат-бота.

## 4. Граф знаний

**Два слоя:** глобальная версионируемая онтология + пользовательский срез.

**Узлы:** `Technology`, `Topic`, `Concept`, `Skill`, `User`, `Vacancy`, `Resume`, `Question`, `Mistake`.

**Рёбра:**

- `REQUIRES` / `PREREQUISITE_OF` — зависимости тем (SQL → PostgreSQL → Query Optimization)
- `RELATED_TO` — слабая ассоциация
- `PART_OF` / `SUBTOPIC_OF` — иерархия
- `COVERS` — тема покрывает концепт
- `HAS_SKILL_STATE` — пользовательский слой: `User → Topic` с `proficiency`, `confidence`, `source`, `last_assessed`, `evidence`
- `MENTIONS` — вакансия/резюме упоминает навык
- `ANSWERED_IN` / `CAUSED_BY` — ответ ↔ тема ↔ ошибка

**Как используется:** построение профиля · gap-анализ · маршрут обучения (топосорт по `REQUIRES`) ·
адаптация в сессии (спуск к пререквизиту при провале) · дедупликация вопросов.

**Хранение:** реляционная модель в Postgres на MVP; доступ через репозиторий-границу,
чтобы позже переехать на Neo4j / Apache AGE без переписывания агента.

## 5. Модель данных (минимум)

```
users
  ├─ 1:N resumes ── 1:N resume_skills
  ├─ 1:N interview_sessions ── 1:N interview_turns
  │                          └─ 1:N agent_actions
  ├─ 1:N user_skill_states (user_id, topic_id, proficiency, confidence, source, updated_at)
  └─ 1:N learning_plans ── 1:N plan_items

vacancies ── 1:N vacancy_skills
topics ── 1:N topic_prerequisites (self-join, REQUIRES)
embeddings (pgvector: source_type, source_id, vector, model, metadata)
```

Ключевое: `user_skill_states` — материализованный срез графа; `agent_actions` — обязательный audit-лог.

## 8. План разработки (8 недель)

### Вехи

| Веха | Недели | Готово, когда |
|---|---|---|
| M0. Фундамент | 1 | Сервис поднимается, БД и auth работают, LLM отвечает |
| M1. Агент-ядро | 2 | Агент вызывает инструменты в цикле + пишет лог |
| M2. Понимание кандидата | 3–4 | Вакансия и резюме → профиль знаний с пробелами |
| M3. Подготовка | 5 | Персональный план + рабочая сессия интервью |
| M4. Адаптивность | 6 | Вопросы и сложность подстраиваются под ответы |
| M5. Память и отчёт | 7 | Отчёт по сессии + переиспользование профиля |
| M6. Демо | 8 | Сквозной сценарий проверяем и воспроизводим |

### Задачи по неделям

**Неделя 1 — Фундамент.**
Репозиторий (monorepo: `/backend`, `/frontend`, `/infra`) · Docker Compose (Postgres + pgvector) ·
скелет FastAPI + `/health` · Alembic + начальная схема · JWT-auth · слой LLM-провайдера
со структурным выводом. Frontend: каркас React + TS + Vite, роутинг, shadcn/ui.
*Готово: поднимается одной командой, логин работает, LLM возвращает JSON по схеме.*

**Неделя 2 — Agent Harness.**
Граф состояний LangGraph + checkpointer · реестр tools (JSON Schema) · исполнитель tool-calls ·
таблица `agent_actions` · лимиты и таймауты · тесты на мок-LLM. Frontend: экран входа, каркас дашборда.
*Готово: с мок-LLM цикл проходит и пишет лог.*

**Недели 3–4 — Понимание кандидата.**
Онтология v1 (5–8 тем с зависимостями) · `extract_vacancy_requirements`, `extract_resume_skills` ·
нормализация через эмбеддинги · таблица `user_skill_states` · gap-анализ · экран загрузки, профиль знаний.
*Готово: корректные навыки и профиль с пробелами.*

**Неделя 5 — Подготовка.**
Упрощённый планировщик (приоритизация, без полного топологического маршрута) ·
`learning_plans` / `plan_items` · API плана · экран плана · каркас сессии интервью (WebSocket).
*Готово: план строится, сессия создаётся.*

**Неделя 6 — Адаптивность (самое тяжёлое).**
`next_question`, `evaluate_answer` (рубрики), `adjust_difficulty` · обновление графа по ответу ·
`interview_turns` · стриминг + карточка фидбека.
*Готово: диалог «вопрос → ответ → оценка → следующий вопрос с учётом результата».*

**Неделя 7 — Память и отчёт.**
`save_interview_result` + отчёт · `load_user_profile` + переиспользование · экран отчёта ·
дашборд прогресса · таблица `embeddings`.
*Готово: отчёт есть, новая вакансия видит прошлый опыт.*

**Неделя 8 — Демо и проверка.**
E2E-тест сценария · mini-eval (3–5 эталонных примеров) · багфикс · тестовые данные · README · демо-прогон.

### Критический путь

`Agent Harness` → `Извлечение` → `Профиль` → `Интервью (оценка + адаптация)` → `Память`.

Если отстаём — режем UI-полировку, E2E и дашборды, **но не цикл агента**.

## 9. Тестирование

- **Функциональное:** REST/сервисные тесты, golden-наборы вакансий и резюме, CRUD, auth.
- **Агентское:** цикл завершается за N шагов; корректный выбор инструментов (мок-LLM);
  валидация схем `tool_call`; audit-лог пишется всегда; откат при ошибке инструмента.
- **Сценарное (e2e):** все 7 шагов пользовательского сценария; повторный запуск с новой
  вакансией использует профиль; параллельные сессии.
- **Адаптивность:** синтетические пользователи (слабый в SQL / сильный в Python) — агент
  предсказуемо меняет сложность и темы; регрессия оценок после N сессий; согласованность с эталоном.
- **Качество LLM:** eval-наборы на извлечение (precision/recall) и на оценку ответов.

## 10. Риски и решения

| Риск | Решение |
|---|---|
| Точность оценки ответов | Рубрики + структурный вывод + самоконсистентность + калибровка на эталонах; хранить `confidence` и `evidence` |
| Качество онтологии | Узкая курируемая онтология на старте; расширение из вакансий с ревью; версионирование |
| Застревание / дороговизна agent-loop | Лимиты итераций и бюджета, таймауты, checkpointing, дешёвая модель для рутины, fallback-ответ |
| Дрейф профиля | Взвешенное обновление (веса по `source`, decay), пересчёт по истории |
| Раздувание контекста | Суммаризация сессий, извлечение только релевантного среза графа, RAG вместо «всё в промпт» |
| Рассинхрон графа и БД | Единая транзакция; граф — источник расчётов, `user_skill_states` — срез |
| Приватность | AuthN/AuthZ, изоляция по `user_id` на уровне tools, шифрование чувствительных данных |
| Латентность стрима | Стриминг токенов, очередь, отдельный воркер агента, кэш эмбеддингов |
| Потеря контекста между сессиями | Жёсткая фиксация состояния в БД/checkpoint, недельные спринты, чёткие Definition of Done |
| Скоуп-крип | Замороженный список из 8 блоков; отложенные фичи не тянуть в MVP |

## 11. Зафиксированные решения (Decision log)

| Решение | Обоснование |
|---|---|
| Модульный монолит, не микросервисы | Скорость разработки, минимум инфраструктуры |
| LangGraph как Harness | Явный граф состояний + checkpointing + контроль tool-calling |
| Postgres + pgvector, одна БД | Меньше инфраструктуры; векторный поиск без второй системы |
| Граф в Postgres на MVP | Реляционная БД по требованию; репозиторий-граница для будущей миграции |
| React + TS, а не Python-UI | Реалтайм-стриминг интервью, кастомные визуализации, качественная кодогенерация агентом |
| Без state-менеджеров | TanStack Query + `useState` закрывают 80% потребностей |
| Упрощённый планировщик в MVP | Полный маршрут по графу — на расширенной версии |
| JWT auth | Просто и стандартно |

**Отложено:** Neo4j/AGE · RAG · визуализация графа · второй LLM-провайдер ·
spaced repetition · мультиагентность · голос и таймеры · предиктор готовности.

## 13. Правила работы агента в этом репозитории

- Не нарушать архитектурные правила (LLM не обращается к БД напрямую и т.д.).
- Каждый инструмент — с JSON Schema, валидацией и записью в audit-лог.
- Новое состояние — только через миграции Alembic.
- Frontend: не добавлять state-менеджеры, анимации и кастомные визуализации без явного запроса.
- Фича считается готовой только при наличии теста и прогона через реальный сценарий.
- При неоднозначности — предлагать варианты с компромиссами, а не выбирать молча.
